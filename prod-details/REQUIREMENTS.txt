TRAVEL PLANNER + EXPENSE TRACKER - IMPLEMENTATION REQUIREMENTS
Release: CBC 2.0 hackathon baseline v3
Database: Neon PostgreSQL + PostGIS
Authentication: Neon Auth (managed) - NOT a self-hosted Better Auth implementation
Hosting: Vercel

================================================================
0. NON-NEGOTIABLE IMPLEMENTATION DECISIONS
================================================================

1. Use Neon Auth through @neondatabase/auth and its supported Next.js
   integration. Do not install/configure a separate better-auth server.
2. Do not create duplicate auth/user/session/account/verification tables
   in the app schema. Neon Auth manages its own neon_auth schema.
3. The app-owned profile table stores the Neon Auth session user ID and
   product-specific profile values. It must not store passwords/tokens.
4. All database operations happen on the server. Every trip-scoped
   endpoint checks authentication and active trip membership. Owner-only
   operations also check the owner role.
5. Do not embed secrets in source code, Markdown, prompts, screenshots,
   client bundles, or version control. Keep .env* in .gitignore and commit
   only .env.example with blank values/placeholders.
6. Money is stored as integer paise. Expense + split rows must be written
   atomically, and optimistic version checks must prevent lost updates.
7. AI cannot invent place IDs or authoritative route times. Validate all
   structured AI output, then run the deterministic conflict checker.
8. Implement the core demo before any stretch feature.

3. NEON AUTH INTEGRATION
================================================================

Install the supported Neon Auth integration packages; use the package's
current official Next.js documentation if API details have changed:

  pnpm add @neondatabase/auth @neondatabase/auth-ui

Expected integration responsibilities:
- Browser auth client points to the current branch's Neon Auth URL.
- Server auth integration uses createNeonAuth from
  @neondatabase/auth/next/server.
- Expose the supported handler at app/api/auth/[...path]/route.ts.
- Use the SDK's session lookup in server components/handlers.
- Configure the supported proxy.ts middleware for route/session handling.
- Generate a secret for Neon Auth's server cookie/session caching.
- Use the returned Neon Auth user ID as app profile.user_id.
- Configure email/password and verification behaviour through Neon Auth.
  No separate email provider (Resend/SMTP) is part of the hackathon.
- Keep DOB and trip preferences in the app-owned profile table, not in
  custom password/auth tables.

Do NOT:
- install or configure `better-auth` as the application's auth server;
- create BETTER_AUTH_SECRET or BETTER_AUTH_URL;
- manually hash or store passwords;
- write directly to tables in Neon's managed neon_auth schema;
- rely on middleware alone instead of validating membership in APIs.

8. DATA MODEL REQUIREMENTS
================================================================

Neon Auth-managed data (do not create app copies):
- neon_auth schema managed by Neon Auth.
- Do not define local user/session/account/verification/password tables.

App-owned tables:
- profile(user_id, display_name, date_of_birth, vibe_tags, pace,
  budget_level, created_at, updated_at)
- trip(id, owner_id, type, people_count, destination, timezone, start_date,
  end_date, daily_start, daily_end, transport_mode, budget_paise, status,
  join_code, version, created_at, updated_at)
- trip_member(trip_id, user_id, role, joined_at, removed_at)
- place(id, name, category, location, destination, source, opening_hours,
  hours_confidence, description, image_url, image_author, image_license,
  popularity_score, verified, created_by)
- itinerary(id, trip_id, status, version, updated_by, updated_at)
- stop(id, itinerary_id, place_id, day_index, start_time, end_time,
  sort_order, est_cost_paise, notes)
- route_cache(origin_key, destination_key, mode, duration_s, distance_m,
  fetched_at, source, is_approximate)
- expense(id, trip_id, payer_id, amount_paise, category, note, spent_at,
  split_type, version, created_by, created_at, updated_at)
- expense_split(expense_id, user_id, share_paise)
- settlement(id, trip_id, from_user, to_user, amount_paise, status,
  created_at, settled_at)
- Optional stretch tables: checkin, branch, branch_member,
  branch_stop_change, expense_audit.

Indexes/constraints:
- GiST index for place coordinates if PostGIS is enabled.
- Search index for place names.
- Index trip_id on trip-scoped tables.
- Unique join_code; unique active membership per trip/user.
- One current itinerary per trip unless a version/history model is deliberately
  implemented.
- Foreign keys between app-owned tables.
- Check constraints for positive budget/expense, positive duration, and
  non-negative split shares where practical.

================================================================
10. FAILURE HANDLING AND CACHE RULES
================================================================

- Neon Auth failure: show clear error; never bypass authentication.
- Database timeout/cold start: loading state and one safe retry where
  duplicate writes cannot occur.
- ORS failure/quota: cache first, then straight-line estimate and label it
  approximate.
- LLM failure/rate limit/invalid JSON: retry one time; then deterministic
  schedule and show that AI-generated descriptions are unavailable.
- Weather failure: hide panel or show unavailable state.
- Empty place search: present the custom-place entry flow.
- Stale itinerary/expense write: HTTP 409 with a reload/reconcile action.
- Invalid join code: safe error; do not reveal private trip information.
